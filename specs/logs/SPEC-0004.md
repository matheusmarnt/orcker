## S2 — plan

### Decisions taken before writing code

**D1 — the wire types live in `orcker-ipc`, and `orcker-engine` depends on it.**
Precedent: `orcker-doctor` is a pure crate that consumes `orcker_ipc::Diagnosis`.
Direction stays downhill (`orcker-engine` to `orcker-ipc` to `orcker-core`) and
`bollard` never enters the contract crate's graph. R2's model is therefore
expressed once, as `orcker_ipc::DockerStatus`, and assembled by
`orcker-engine`'s pure layer.

**D2 — the docker section reaches `orcker status` through a second IPC round
trip, not through a new `StatusReport` field.** R6 words it that way, and the
alternative is out of surface: `StatusReport` is not `#[non_exhaustive]` and is
built with a full struct literal in `crates/orcker-mcp/tests/render.rs`, so a
new field would break a file this spec may not touch. `orcker status` sends
`Status` then `EngineStatus` and renders both from one `Rendered`.

**D3 — `bollard` with no TLS feature at all.** `bollard 0.21.1` has
`default = [http, pipe]`; `ssl` is off by default. Pinning
`default-features = false, features = ["http", "hyperlocal"]` gives the unix
socket client with zero TLS stack, which is stricter than the spec's "rustls
features only" and keeps `bin/orckerd/tests/no_runtime_deps.rs` green.

**D4 — versions get a small pure type, not `semver`.** Docker and compose do not
report strict semver (`v2.29.7`, `27.4.0-rc.1`) and the spec's own minimums are
two-component (`24.0`, `2.20`). `orcker_engine::pure::Version {major, minor,
patch}` parses a leading `v`, two or three components and a trailing
`-rc.1`/`+build` suffix, and derives `Ord`. The wire carries rendered strings so
`orcker-ipc` gains no version dependency.

**D5 — `Request`/`Response` are `#[non_exhaustive]`,** so the new variants
cannot break the GUI or `orcker-mcp` (both already carry wildcard arms). The
inline exhaustiveness tests in `request.rs`/`response.rs` are inside the surface
and get one arm each.

## S4 — implement

### Deviations from the S2 plan

**`Response::EngineStatus` carries a `Box<DockerStatus>`, not the value.**
Inline, the new variant became the largest in the enum and every
`Result<_, Response>` in `bin/orckerd/src/ipc_server.rs` tripped clippy's
`result_large_err` ("the `Err`-variant is at least 136 bytes", three sites).
`Response::Status` already boxes its report for exactly this reason.
`Box<T>` serializes transparently, so the pinned wire bytes did not move — the
AC4 literals passed unchanged after the box.

**`bollard` needs `features = ["http", "pipe"]`, not `["http", "hyperlocal"]`.**
`Docker::connect_with_socket` sits in an
`#[cfg(all(feature = "pipe", any(unix, windows)))]` impl block, so `hyperlocal`
alone does not expose the unix-socket constructor. `pipe`'s Windows half
(`hyper-named-pipe`) is already `[target."cfg(windows)".dependencies]` upstream,
so the change costs nothing on Linux/macOS and still enables no TLS feature.

## S7 — supervisor, attempt 0: REWORK

Deterministic layer DT1-DT9 all pass. Two judgment findings; `attempts` bumped

### JG1 (R5) — the version floor had two sources of truth

`hint_for` spelled `24.0` and `2.20` out in prose while
`MIN_ENGINE_VERSION` / `MIN_COMPOSE_VERSION` held the real floor, so bumping a
constant would have shipped a hint telling the user to upgrade to the version
they already had - wrong text in exactly the output NFR-08 exists for.

Fixed by making `hint_for` return `String` and interpolate the constants (the
sibling `message` in `assemble` already did), plus two assertions in
`minimum_version_policy` so the duplication cannot come back. RED for the new
assertion, produced by restoring the hardcoded string:

```
thread 'pure::tests::minimum_version_policy' panicked at crates/orcker-engine/src/pure/mod.rs:192:9:
the floor has one source of truth: the hint must name MIN_ENGINE_VERSION, not a
hardcoded copy that a constant bump would leave stale
test result: FAILED. 0 passed; 1 failed
```

### JG6 (R8) — the CLI invented a cause it could not know

`run_status` collapsed every non-`EngineStatus` outcome into `None` with
`_ => None`, and the renderer then printed "the daemon predates the docker
section". In this fork the CLI and daemon ship together, so a transport failure
or a `Response::Error` is the likely cause, and the invented explanation would
send the user after the wrong problem while the real error was discarded.

Fixed by extracting `map::docker_section`, a pure function from the exchange
outcome to `(section, note)`: the section is still simply absent (exit code
unchanged, R8) but the real reason now goes to stderr, and the placeholder line
no longer names a cause. Covered by the new
`a_failed_engine_status_exchange_names_its_own_cause` (four outcomes: good
answer, `Response::Error`, unexpected variant, transport failure) and by a
regression assertion in `status_without_a_docker_section_still_renders`. RED for
that assertion, produced by restoring the old line:

```

the CLI cannot know why the section is missing, so it must not blame version skew
```
