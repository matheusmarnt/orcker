## ESCALATE 1 — R1 vs the tunnel (resolved: fold)

**Diagnosis.** R1 orders the deletion of `crates/orcker-supervise`, but
`orcker-tunnel` — kept by "Out of scope" and scheduled for regression by
FR-120/SPEC-0026 — is a live compile-level consumer:

```

crates/orcker-tunnel/src/manager.rs:525: use orcker_supervise::supervisor::{KillSignal, StopProtocol};

`orcker-supervise` is not native-runtime code: its module doc calls it a
"process-agnostic supervision substrate ... depends on nothing internal", and
the FPM-vs-database timing difference is supplied per call through
`supervisor::SupervisorPolicy`. PHP-FPM and the DB engines were two of its three
consumers; the tunnel is the third and it survives this spec.

**First proposal (keep the crate) was withdrawn after reading the PRD.**
`docs/PRD.md:96-97` states FR-002 as *"Crates `yerd-php`, `yerd-services` e
`yerd-supervise` removidas do grafo de runtime"*, AC1 *"workspace compila e
testa verde sem as três crates"*. Keeping the crate fails both the main clause
(it would stay in the runtime graph via the tunnel) and AC1 literally, and
`docs/PRD.md:246` forbids agents editing the PRD — it would have needed a
`docs/rfc/` proposal plus a PRD minor bump before this spec could be accepted.

**Resolved (human, 2026-08-22): fold.** Delete the crate and move its five
modules into `crates/orcker-tunnel/src/supervise/`. Scores against both truth
documents:

|---|---|

| PRD FR-002 AC2 (no native PHP/DB process) | satisfied — `cloudflared` is neither |
| PRD:14 + FR-120 (tunnel kept) | satisfied |
| PRD §246 (no agent edits to the PRD) | no PRD change needed |

## ESCALATE 2 — R4 vs SDD DT5 (resolved: R4 stands, exception recorded)

**Diagnosis.** R4 resets the wire contract (`PROTOCOL_VERSION` 1 -> 2,
`tests/wire_stability.rs` re-baselined). SDD §8.1 **DT5** reads *"IPC: testes de
wire-stability intocados e verdes; mudanças de protocolo apenas aditivas"* and
carries no escape clause, so the supervisor would REWORK mechanically.

**Technical basis for keeping R4.** `PROTOCOL_VERSION` never travels on the
wire: `crates/orcker-ipc/src/lib.rs:8-21` defines a frame as a 4-byte
big-endian length plus JSON, with no handshake, and the const's own doc says
"Bump on any breaking change; add a handshake before doing so". The bump is a
semantic marker with zero runtime effect. The runtime risk that does exist —
`Request` is `#[serde(tag = "type")]` with no fallback variant, so an unknown
tag during an upgrade window decodes as `IpcError::Decode` rather than a typed
error — is unchanged by the bump and predates this spec.

Backward compatibility protects nobody here: the workspace is `version =
"0.0.0"`, `publish = false`, no release exists, and SPEC-0001 renamed the IPC
endpoint and directory qualifier (`io.yerd.Yerd` -> `io.orcker.Orcker`), so an
installed Yerd daemon does not even share a socket. The additive alternative
that FR-002 also permits would keep roughly 45 zombie request variants alive,
each needing an `unsupported` arm in the daemon, plus `PhpPoolStatus`,
`ServiceStatus` and `DatabaseSummary` alive so `StatusReport` still
deserializes — permanent complexity rented to zero tenants, and a direct
contradiction of FR-002's own main clause.

**Resolution.** PRD FR-002 explicitly allows *"comandos/mensagens IPC
correspondentes **removidos** ou marcados `deprecated` de forma aditiva"*, and
SDD §5 gives the PRD precedence on the *what*. R4 stands; the DT5 exception is
recorded in `specs/DECISIONS.md` so the supervisor reads it before judging.
Two guardrails attach to it:

1. `tests/wire_stability.rs` (3312 lines of byte-exact literals) is edited by
   **deletion only**. The `#[test]` functions of removed variants go; every
   surviving literal stays byte-identical; `git diff` on the file must be pure
   deletions. Regenerating it is what would let a typo in a kept variant's
   literal ship as a silent protocol bug.
2. The `PROTOCOL_VERSION` doc comment is corrected: the constant is
   informational until a handshake exists. The handshake itself, and a
   `#[serde(other)]` fallback so version skew yields a typed error instead of a
   decode failure, are drafted separately — out of this surface.

## S4 — P2a finding: the deleted crate held non-PHP infrastructure

Found while enumerating the IPC surface for P2, before any edit. Not an
escalation (no product ambiguity, no PRD conflict, diff stays in `surface`) but
it changes the order of operations, so it is recorded here.

`orcker-php` was two things at once: the PHP runtime, and the workspace's
download/unpack substrate. Deleting it whole would take the substrate with it,
and every surviving consumer of the substrate is a feature this spec explicitly
keeps.

| Surviving consumer | Needs from `orcker_php` |
| --- | --- |
| `bin/orckerd/src/self_update.rs` | `Downloader` |
| `bin/orckerd/src/tools/{mod,composer,node,bun}.rs` | `Downloader`, `DownloadError`, `current_os_arch`, `Os`, `Arch`, `is_safe_member` |
| `bin/orckerd/src/tunnel/install.rs` | `current_os_arch`, `Os`, `Arch`, `Downloader` |
| `bin/orckerd/src/tunnel/named.rs` | `io::atomic_write::write` |
| `bin/orckerd/src/wordpress_versions.rs` | `Downloader` |
| `bin/orckerd/src/service_install.rs` | `is_safe_member` (dies with R1, listed for completeness) |

Two further facts from the same read:

- `orcker_php::traits` was a six-line re-export shim: `Downloader`,
  `DownloadError`, `Clock`, `ProcessSpawner` and friends were `orcker-supervise`
  symbols. P1 already carried them into `crates/orcker-tunnel/src/supervise/`.
- `ReqwestDownloader`, the only production `Downloader` impl, lives in
  `bin/orckerd/src/php_install.rs`, which P3 deletes.

**Decision.** Same shape as ESCALATE 1: the feature dies, the substrate moves.

1. `crates/orcker-platform/src/pure/artifact.rs` (new, pure, no new deps) takes
   `Os`, `Arch`, `current_os_arch` and `is_safe_member`. Which prebuilt artifact
   this machine needs, and whether an archive member is safe to unpack, are
   platform questions, not PHP ones. `std::env::consts::{OS, ARCH}` are
   compile-time constants, not runtime env reads, so the module stays pure.
2. `bin/orckerd/src/download.rs` (new) takes the `Downloader` trait,
   `DownloadError` and `ReqwestDownloader`. This is the I/O edge and `reqwest`
   is already a daemon dependency.
3. `Downloader` and `DownloadError` are **deleted** from
   `crates/orcker-tunnel/src/supervise/`: the tunnel crate never used them
   itself (verified by grep), it only inherited them from `orcker-supervise`
   because `orcker-php` did. Net deletion there.
4. `orcker_php::io::atomic_write` has one surviving caller, `tunnel/named.rs`;
   `crates/orcker-config/src/io.rs` already does atomic writes. Resolved at P3
   against the existing helper rather than by moving a second copy.

Order becomes P2a (this rescue) -> P2b (IPC surface) -> P3.

**Status:** S4 in progress — P2a starting.

## S4 — P2a finding 2: site creation is native-runtime-bound (spec R2 amended)

Same read, second consequence. `bin/orckerd/src/php_install.rs` dies with R1,
so every caller of `cli_binary_path` / `cli_phprc` must be fixed or deleted.
Measured:

```
$ rg -l 'cli_binary_path|cli_phprc|php_bin|php_cli' bin/orckerd/src

bin/orckerd/src/tools/{laravel,wp_cli}.rs
bin/orckerd/src/{wordpress_url_sync,wordpress_users,services,ipc_server,php_install}.rs
```

These are not incidental references: each one spawns the installed PHP binary.
PRD FR-002 AC2 is "nenhum binário resultante inicia processos PHP/DB nativos",
which they violate by definition.

`orcker_ipc::Framework` has exactly two variants, `Laravel` and `Wordpress`.
Laravel scaffolds through the PHP-based installer, WordPress through WP-CLI plus
a provisioned native MySQL/MariaDB. There is no third, PHP-free path, so site
creation cannot survive the native runtime's removal in any partial form.

The PRD already decided where it goes: **FR-020 (M, F1) — `orcker new`** rebuilds
it "via container, sem Composer no host". So this is deletion, not redesign, and
no PRD change is needed.

**Spec amendment (R2).** R2 named only FPM pools, the service manager and PHP
release checking. It is extended to the site-creation surface that spawns the
PHP CLI: `create_site/`, `tools/{laravel,wp_cli}.rs`, `wordpress_users.rs`,
`wordpress_url_sync.rs`, `wordpress_versions.rs`, and the IPC requests that only
those handlers serve. The generic job machinery (`JobStatus`, `JobCancel`) stays
- tool installs and the cloudflared install still stream through it.

Rejected alternative: keep `CreateSite` as a typed "not yet implemented"
error, mirroring R3's `use <site> <ver>` escape clause. Rejected because R3's
clause exists to avoid disproportionate surgery on a clap tree, while here the
2186 lines behind the request would be dead code with no caller until FR-020
replaces them wholesale. Deleting is both the smaller diff and the honest one.

## S7 — attempt 5: the AC3 fix was itself incomplete

```

My first run of that cross-check reported 77, because I extracted only

### The lesson, and the fix

A pattern file is a list someone wrote. It can always be missing a class - that
is now twice in this cycle. The check the supervisor named is *complete by
construction*: it compares the two real sides of the contract, so no class can
escape it because nobody thought of it.

So AC3 is now two criteria, and the GUI half is **a test, not a grep**:

- `apps/orcker-gui/tests/commandContract.test.ts` reads `generate_handler![]`
  and every `.ts`/`.vue` under `src/`, and fails on any invoked command that is
  neither registered nor enumerated in `ipc/dangling-commands.json`.
- Two further assertions keep the list honest in both directions: no entry that
  is registered again, no entry that is no longer invoked.
- `dangling-commands.json` is a **ratchet**, the same shape as this repo's
  `clippy-allow-baseline.txt`: the known 49 are listed so the test can fail on
  the fiftieth. Its header says removal is the only allowed direction.

It reports the offending name *and its call site*, which is what makes it usable

## Cycle retrospective

Six REWORKs and one ESCALATE on one spec. Worth recording why, because the gate
was green for every one of them.

Every rejection was the same defect wearing different clothes: **something the
removal left dangling that no automated check could see.** Deleted tests that
still covered live behaviour. Doc comments naming removed items. A GUI client
invoking commands the daemon no longer registered. A routed page rendering a
wizard whose backend was gone. Nav items and chords pointing at deleted routes. A
tray menu doing the same from Rust, where the guard I had just written could not
read.

Three things generalise:

1. **A green gate is evidence about what the gate measures, nothing more.** AC3
   grepped three crate names and passed while 25 references dangled. The fix was
   not a better grep - it was noticing the criterion was aimed at the wrong set.
2. **Prefer a check that is complete by construction over a list someone wrote.**
   The pattern file missed a class twice. The invoke-vs-`generate_handler` check
   compares the two real sides of a contract, so no class can escape it for want
   of imagination.
3. **A guard written only in the language it guards is theatre.** That cost the
   last round outright.

The specific failure mode on my side was scripting a judgement call: I deleted
tests by name-matching across 38 000 removed lines and verified with `cargo
check`, which is structurally incapable of catching a test that compiles and
passes while covering nothing. Measuring it later put a number on it - a
compiler-based classifier discards 4 live tests out of 5.

Three tests in this diff asserted the *shape* of what the code currently was
rather than the property it must hold (`catalog_names_are_pinned`,
`response_status_byte_shape`, `registry.test.ts`'s `[1..9]`). The last one was
actively holding a bug in place: it would have failed on the correct fix and
passed on the broken state.

What leaves the cycle stronger than it entered: two contract guards that did not
exist before, each with recorded RED, each catching a class the gate was blind to;
five follow-up specs (0033, 0035, 0036, 0037, 0038) with enumerated, mechanically
checkable acceptance instead of prose; and two of them blocking the Docker work so
none of it starts on unaudited ground.
