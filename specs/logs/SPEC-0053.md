## S2 — plan

Three holes, three separate layers. Nothing here is a new mechanism: each
requirement re-points an existing guard at the project path that skipped it.

### R1 — the loop guard reaches `LinkProject`

`is_self_forward` already answers "is this a loopback target on a port Orcker
itself bound?", but it takes a URL string, and `handle_link_project` has a
`ContainerProject`, not a URL. Rather than format a URL to re-parse it, the
loopback-and-bound-port predicate moves into
`targets_bound_listener(&UpstreamTarget, &[u16])` and `is_self_forward` becomes
its URL-parsing front door. `handle_link_project` then asks the same question of
`project.proxy_site()`'s target — literally the entry the router would insert —
and returns `InvalidPath` with the `AddProxy` message.

The check sits after `plan_link`, not in the dispatch arm, because the port is
only known after planning: without `--port` it is allocated. `AlreadyLinked`
stays untouched; SPEC-0006 R5 makes a relink a no-op and a no-op adds no route.

### R2 — `--port` is range-checked

`plan_link` gains `LinkError::PortOutOfRange { port, first, last }`, checked in
the `Some(requested)` branch against `FIRST_PROJECT_PORT..=LAST_PROJECT_PORT`
(the same constants `allocate_port` already draws from, so the two paths cannot
disagree). Port 0 fails the same check — no separate zero case. `orcker-ipc` is
outside the surface, so the wire code is the existing catch-all `InvalidPath`.

### R3 — `Config::validate` gains project invariants

`validate_projects` joins the chain next to `validate_proxies` and mirrors it:

| Invariant | Reason |
|---|---|
| two projects share a name | `ProjectNameCollision` |
| a project name collides with a linked site or a proxy | `ProjectNameCollision` |
| two projects share a port | `ProjectPortCollision` |
| a project port is 0 | `ProjectPortZero` |

Three reasons for four invariants because `ProxyNameCollision` — the precedent
the spec names — already merges "duplicate" and "collides with a site" into one
reason. The full `20000..=29999` range is *not* enforced here: R3 asks only for
non-zero, and R4 requires configs that satisfy the invariants to keep loading, so
a port SPEC-0006 already persisted must not be retroactively rejected at load.

### R4 — additive

The three reasons are new `ValidateErrorReason` variants on a `#[non_exhaustive]`
enum, and no serialised shape changes, so `tests/toml_byte_shape.rs` is not
touched.

ephemeral port would be refused for being out of range and prove nothing.
