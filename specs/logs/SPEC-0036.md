## S1 — trigger

SPEC-0002's amended AC3 (a symbol-level scan of the whole tree against
`specs/logs/SPEC-0002-removed-symbols.txt`) found GUI surfaces still invoking
Tauri commands whose handlers that spec deleted. No automated check saw them:
`npm run test` mocks the IPC client, `npm run build` never validates a command
name string, and the Rust side is internally consistent with itself. The
failure appears only when a user clicks - worst case the routed site-creation
wizards, which submit to the deleted `create_site`.

- All 49 dangling command strings live in exactly one file,
  `src/ipc/client.ts`, wrapped 1:1 by 49 exported functions. 20 other files
  consume those functions. Deleting the wrappers turns an invisible runtime bug
  into `vue-tsc` errors, which then drive the rest of the removal.

  have no mount point anywhere - SPEC-0002 already deleted the views that used
  them. Whole-file deletes with their tests.

  call. The scan is the work list, as R0 says.
- `JobId` and `JobState` both live inside `create.rs` (l.20, l.214), so R3
  shrinks that file rather than deleting it. No `.rs` file is added, deleted,
  moved or renamed, so `scripts/clippy-allow-baseline.txt` needs no
  regeneration this cycle.

Two R5 stub-or-remove calls, decided with the human before implementation:

- **WelcomeView step 2 (PHP install): removed, steps renumbered** (3-5 become
  2-4). Onboarding must not offer an action that cannot run; PHP returns via
  containers under FR-020.

  `siteUrl.ts` becomes unused and is removed with its two test cases, ledgered

- `WindowScope` loses `"dumps"`: nothing renders that window after R2, and a

## S8 — escalation resolved: R1 given an executable criterion

The human authorised amending R1. Before choosing, the ratchet the supervisor
recommended was **built and run**, and its own output refuted it:

- 96 exports were already dead at `HEAD`, 84 after the diff. An absolute
  "no dead exports" gate needs an ~84-entry allowlist - 26% of the tree's 320
  exports. That is a rubber stamp, not a guard.
- It reports live code as dead. `jobStatus` is called by `pollJobToEnd` in the
  same file: unreferenced *outside its home file* is not the same as unused.
- Fatal: 9 of its hits live in `src/ipc/types.ts`, a wire-contract mirror whose
  exports mirror daemon `Response` variants whether or not the GUI consumes each
  one today. One of them is `JobState`, which **R3 explicitly orders kept**. The
  gate would have demanded deleting what the spec mandates keeping.
- No dead-code tool is installed (`knip`/`ts-prune`/`depcheck`: none), so it also
  meant a new dependency for what two existing files already do in ~80 lines.

**The criterion adopted instead is the delta, not the absolute:**
`dead(working tree) \ dead(HEAD)`, in `tests/dead-export-delta.mjs` (R0b, AC6).
It is executable, so R1 finally has a completeness check; it excludes the 96
inherited exports automatically (SPEC-0037's debt, not this spec's); and it
cannot contradict R3, because a deliberate keep is a justified line here rather
than an allowlist entry. Not a vitest file: the answer depends on `HEAD`, so it
is cycle evidence, not a standing gate.

**It immediately outperformed three rounds of reading.** Three supervisor rounds
found 2 orphans; the first run found 5:

| symbol | sole consumer at `HEAD` | action |
| --- | --- | --- |
| `WORDPRESS_LOCALES` | `CreateWordPressWizard.vue` | file deleted |
| `TEXT_SETTINGS`, `DISPLAY_ERRORS_HINT` | `PhpVersionPanel.vue` | `phpSettings.ts` + its test deleted |
| `jobCancel` | both wizards | deleted |
| `pickExtensionFile` | `AddExtensionModal.vue` | deleted |

Then it caught something no one had: deleting `wordpressLocales.ts` orphaned
`ComboboxOption`, whose only external consumer that file was

one-shot read cannot see, because it does not exist until the first deletion
lands. `Combobox.vue` is still mounted by `IntegrationsView` and still uses the
type internally, so the fix is to drop the `export`, not the type. Same

**AC6 evidence.** Before: `orphaned 15`. After: `orphaned 9`, and all 9 are in
`src/ipc/types.ts`.

**Justification for the 9 keeps** (R0b requires one, and one covers all nine):
`AddableServiceType`, `AvailablePhpResponse`, `JobState`, `PhpExtInfo`,
`PhpVersionsResponse`, `ServiceAvailability`, `ServiceStatus`,
`WordPressAdminUser`, `WordPressVersionInfo` are `Extract<>` aliases over members
of the `Response` union, and they stand or fall with those members.

Precision the supervisor corrected me on at round 4, worth keeping straight:
only `JobState` is live contract-mirror surface - `crates/orcker-ipc/src/create.rs`
still defines it and R3 mandates it. The other eight have **no Rust counterpart
at all**: the wire tags `php_versions`, `available_php`, `wordpress_admin_users`
and `wordpress_versions` appear zero times in `crates/orcker-ipc/src`. They
mirror a contract SPEC-0002 already deleted. So "contract mirror" is the wrong
word for those eight - the right one is *stale union members under someone
else's spec*. The decision to keep them is unchanged and still correct: they are
aliases over `Response` members that this cycle deliberately left to
SPEC-0034/0035 under the R4 boundary the supervisor accepted in round 1, and
deleting an alias while keeping the member it extracts from would be incoherent -
it would hide the staleness rather than remove it.

**One consequence, recorded rather than hidden.** Deleting `jobCancel` makes the
`job_cancel` host command registered-but-uninvoked, joining `daemon_installed`
and `get_site_ide_overrides`. AC4's direction (invoked but not registered) is
still zero; the reverse direction is SPEC-0039's subject and now names
`job_cancel` explicitly, including why its sibling `job_status` is not in that
class. `pickExtensionFile` has no such effect: it drives the Tauri dialog
plugin, not a `generate_handler!` command.
