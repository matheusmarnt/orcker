## S1 — context

`docs/developer/building.md` tells a contributor to run the from-source daemon
with `cargo run -p orckerd -- -v`. `orckerd` accepts no top-level `-v`:
`bin/orckerd/src/args.rs` has `Cli.command: Option<Command>` and `verbose: u8`
on `ServeArgs`, reached only through the explicit `serve` subcommand. The
documented command therefore fails to parse. Inherited from upstream, found
while gathering SPEC-0001 AC2 evidence, re-confirmed 2026-09-04 against
SPEC-0046 AC3.

Spec front matter at `HEAD` (`git show "HEAD:specs/SPEC-0030-*.md" | awk
-F': ' '/^status:/{print $2; exit}'`): `approved`. `depends_on: [SPEC-0001]`,
which is `accepted`. Selectable.

The approved file carried only `Context` and `Requirements` (R1) - `Design &
contracts`, `Test plan`, `Acceptance checklist`, `Out of scope` and `Agent
notes` were missing, which `docs/SDD.md` section 4 requires before `status:
approved`. `specs/SPEC-0042-*.md` hit the identical gap and this cycle
follows its precedent: the missing sections are authored here because they
transcribe the already-approved Context and R1 rather than decide anything
new - R1 is one mechanical string replacement with no product ambiguity. The
approved `Context` and `Requirements` text is not edited.

## S7 — supervisor, round 1: REWORK

Deterministic layer clean (`[gate] OK`, full workspace suite green, surface
`specs/ docs/`, DT9 confirmed - approval commit `9e9dfce` precedes any
implementation commit). AC1-AC5 as written all re-verified pass. Two judgment
findings, both blocking:

1. **JG1/JG5 - a third stale block survived.**
   `docs/developer/building.md:207` (pre-round-2) still read `cargo run -p
   orckerd -- --config ~/orcker-dev.toml -v`. `--config` lives on `ServeArgs`
   exactly like `-v` (`bin/orckerd/src/args.rs:37-38`), so it fails identically:
   `error: unexpected argument '--config' found`, exit 2. R1 says "every"
   occurrence and "each command block ... actually runs"; this round's AC1/AC2
   were literal greps for the exact string named in the Context
   (`orckerd -- -v`), so they passed at `grep -c 'orckerd -- -v'` = `0` while a
   sibling defect of the same class stood untouched three lines away. Tests
   shaped to the fix instead of the requirement (JG5) - textbook of the
   pattern S4's own note in SPEC-0042 already named a risk for.
2. **JG6 - the round-1 prose "correction" was itself wrong.** Round 1 changed
   "`serve` is the default subcommand" to "`serve` is the subcommand that
   starts it", asserting the former was false. It is true:
   `bin/orckerd/src/main.rs:20` (`cli.command.unwrap_or_else(||
   Command::Serve(ServeArgs::default()))`) and `args.rs:18`'s own doc comment
   both default to `Serve` when no subcommand is given. The actual mechanism
   the guide needed to explain is narrower: clap's top-level `Cli` parser has
   no `-v`/`--config` fields, so it cannot route a bare flag into the default
   `Serve` variant - the default only fires for zero-argument invocations.
   Confusing "is the default" with "flags need it named explicitly" produced a
   factually wrong sentence in a doc this very spec exists to make accurate.

Both are corrected in round 2, in place, no new files:

- `docs/developer/building.md`: the `--config` command line now reads
  `cargo run -p orckerd -- serve --config ~/orcker-dev.toml -v`; the sentence
  above it ("`orckerd` takes `--config` (`-c`)") now says `serve` takes it.
  The Step 3 sentence is rewritten to state the true mechanism (default
  subcommand, but its flags need it named) instead of the false "not the
  default" claim.
- AC1/AC2 generalized from literal-string greps to a pattern that catches the
  whole defect class: `grep -cP 'orckerd -- (?!serve)'` (any `orckerd --`
  invocation *not* immediately naming `serve`), which read `3` at true `HEAD`
  RED and must read `0` after the fix. AC3 extended to cover the third
  command.
- `specs/SPEC-0030-*.md` Design & contracts / Out of scope / Agent notes
  rewritten to state the correct default-subcommand mechanism and to narrow
  the "out of scope: other command blocks" carve-out now that AC1's pattern
  reaches every `orckerd` invocation in the file (round 1's carve-out judged
  blocks "unrelated to the defect", which is exactly the kind of
  by-inspection judgment call JG5 flags as unreliable).
