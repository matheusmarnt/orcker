## S2 — plan and the R2 question

R2 asks for a code delta **only if** the inherited custom-proxy/route mechanism
cannot already express "serve `spike.test` from `http://127.0.0.1:18080`". Read
before touching anything:

- `bin/orcker/src/cli.rs:274` `ProxyAction::Add` — two arguments create a
  whole-host proxy: `orcker proxy add spike http://127.0.0.1:18080`.
- `docs/guide/proxies.md` — a whole-host proxy gets DNS and trusted HTTPS
  through `orcker secure <proxy>`, preserves `Host`, adds `X-Forwarded-*`,
  tunnels websocket upgrades, and answers 502 instead of hanging when the
  upstream is down.
- `crates/orcker-proxy/src/forward/{http,upgrade}.rs` already carry both paths.

So the expected delta is docs + specs only. The declared code surface stays
untouched unless execution disproves this, in which case the delta lands inside
it with the table-driven unit test the spec's Test plan asks for.

### Debugging done on the way (all in the spike stack, none in orcker)

Three failures, each traced to a root cause before any fix:

1. `mbstring` would not configure — `Package 'oniguruma' … not found`. Cause: the
   reference dependency list omits `libonig-dev`. Added.
2. `postgres` exited 1 on first boot. Cause: `postgres:18` moved its data directory;
   the volume has to mount at `/var/lib/postgresql`, not `/var/lib/postgresql/data`.
3. Vite answered `403 Blocked request` through the proxy. Cause isolated by hitting
   Vite *directly* with `Host: vite.test` — same 403, so not a proxy defect but Vite's
   `server.allowedHosts` guard. A first patch appeared not to work; the reason was a
   duplicate `server:` key in `vite.config.js` (the later literal wins), fixed by
   merging into the existing block. Then `101`.

## S5b — elevated, the acceptance closed on real `:443`

`sudo ./target/debug/orcker elevate` (run by the human) set
`cap_net_bind_service=ep` on `target/debug/orckerd`, installed
`/etc/systemd/resolved.conf.d/orcker-test.conf` (`Global: ~test`) and put
`orcker-bb5222a78c274bd3.crt` in the system anchor store. After restarting the
daemon it binds `127.0.0.1:80` and `127.0.0.1:443`.

- `curl -sv https://spike.test/` **without `--cacert`**: `200`,
  `subject: CN=spike.test`, `issuer: CN=Orcker Local CA`,
  `SSL certificate verify ok` - the system store validates it (AC2).
- `curl -sI http://spike.test/` -> `301` to `https://spike.test/`.
- Chrome loads the Laravel 13 welcome page with no interstitial (AC1),
  `evidence/browser-spike-test.jpg`.

Two detours on the way, both traced rather than guessed:

1. `sudo env XDG_…=… orcker elevate` reported `daemon not running`
   (`/tmp/orcker-1000/orcker.sock`). Cause: `bin/orcker/src/elevate.rs:499`
   discards the environment when `SUDO_UID` is set and probes uid-derived
   paths. The `XDG_*` variables were never read. Worked around with
   `ln -sfn /tmp/orcker-dev/run/orcker /tmp/orcker-1000`; the real gap is
   queued as SPEC-0046 and recorded as F8.
2. The browser page rendered unstyled. Cause: a stale `public/hot` left by the
   earlier `npm run dev`, so Laravel's `@vite` pointed at a dev server that was
   no longer running. Removed; the page then loaded
   `https://spike.test/build/assets/app-*.css`, which also confirms
   `X-Forwarded-Proto` reaches Laravel's URL generation.

The latency number was corrected in the same pass: the first measurement ran
against cold opcache (109 ms "direct") and hid the proxy's cost. Warm, it is
31 ms direct vs 113-125 ms proxied, and the difference is the per-request TLS
handshake (`time_appconnect` 40-76 ms) on an unoptimised debug build - not
forwarding overhead.

## Deviations from the reference stack

Recorded here and in the runbook, each with its reason:

- `php:8.4-fpm` instead of `php:8.4-rc-fpm` — 8.4 is stable, the `-rc` tag no
  longer publishes.
- No `laravel-pulse` supervisor program — Pulse is not part of a fresh Laravel
  install, and AC3 only requires fpm + horizon + schedule.
- No external `development` network — the spike keeps every service inside
  `app-network` (spec Agent notes); the shared network arrives in Phase 1.
- `redis` added as a stack service — Horizon needs it and there is no global
  services runtime yet (spec Agent notes).
- Postgres credentials declared inline in `compose.yaml` instead of
  `env_file: .env` — the compose file has to stand on its own in the repo,
  while the Laravel `.env` lives outside it in the scratch checkout.
