## S2 — plan

Full plan: `/home/matheusmariano/.claude/plans/wild-skipping-turtle.md`
(approved). Summary — two escalations resolved with the human before any
code was written (`AskUserQuestion`, both recommended options chosen):

**Spec premise was wrong for `get_site_ide_overrides`.** The spec's Context
said it was "invoked by nothing in `src/`," alongside `daemon_installed`. A
direct grep found `apps/orcker-gui/src/components/SiteDetailsSidebar.vue:156`
calling it live (`await Promise.all([getPreferredIde(), getSiteIdeOverrides()])`),
feeding a mounted, working per-site IDE-override picker (`changeIde` →
`setSiteIdeOverride`) inside `SiteDetailsSidebar.vue`, itself imported and
rendered by `SitesView.vue:841` — not orphaned at any level. `daemon_installed`
and `job_cancel` had zero call sites anywhere (Rust or TS), confirmed
directly. **Decision:** narrow R1 to the two genuinely dead commands, correct
the spec text (commit `af4fbc9`,
`docs(specs): correct SPEC-0039 dead-command and FR-020 premises`), exclude
`get_site_ide_overrides` from this spec.

**R3's product question was genuinely unsettled.** The spec pointed at
`docs/PRD.md` FR-020 to decide the WPA chip's fate; FR-020 is `orcker new`
(project scaffolding), unrelated. A full FR sweep of the PRD found no
requirement covering WordPress admin links at all - `wp_auto_login` is
inherited/undocumented behavior. Per the spec's own instruction ("escalate
rather than improvise if it is not settled there"), escalated. **Decision:**
gate the WPA chip on `site.is_wordpress` instead of `site.wp_auto_login`.
`lib/wpAdmin.ts`'s `openWpAdmin()` already opens the plain, non-auto-login
login screen regardless of `wp_auto_login`, so the click behavior is
unaffected - only the `v-if` changes. Also found, while reading
`SiteCard.spec.ts`, a doc comment noting `SiteDetailsSidebar.vue` already
carries an "always-available" WP Admin entry point separate from this card's
quick-action chip - `site.is_wordpress` gating brings the chip in line with
that existing precedent rather than inventing a new one.

**A latent bug in `commandContract.test.ts` itself, found at S3 (see below):**
`invokedCommands()`'s regex for skipping a call's generic type parameter,
`(?:<[^>]*>)?`, cannot span a *nested* generic. `client.ts:739`'s
`call<Record<string, string>>("get_site_ide_overrides")` has one, so the
scanner silently failed to see that call site - which would have made R2's
new reverse-direction test wrongly flag `get_site_ide_overrides` as
unreachable (it is not; see above). Fixed in the same file R2 already
touches: `[^>]*` → `[^(]*` (exclude the argument list's `(` instead of `>`,
so nested `<...>` is consumed in full). Confirmed no other call site in the
tree uses a nested generic (`grep -rnE '(invoke|call)<[A-Za-z_]+<' src`, one
hit, the one above).
