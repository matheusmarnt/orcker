## S2 — plan

Two areas, two different shapes of fix — neither is a new mechanism.

**AC1 — `EngineStatusCache::get` expiry and write-back.** The probe is not
injectable today (`get` calls `orcker_engine::io::detect_from_env()` inline), so
the expiry path cannot be driven without a real Docker daemon. `get` delegates to
a new private `get_with(probe: impl Future<Output = DockerStatus>) -> DockerStatus`
that owns the freshness decision; `get()` becomes a one-line call passing the real
probe. Stays private — the only caller is `get()`, no new public API.

**AC2 — `run_status`'s two-exchange wiring.** `run_status` is private and prints to
real stdout, so it cannot be called from `tests/cli_e2e.rs` directly. Everything it
wires (`transport::exchange_at`, `map::docker_section`, `map::render_status`) is
already `pub`, so the test drives the identical sequence against the same live
daemon instead of refactoring production code. Extends the existing
`Command::Status` arm in `cli_commands_round_trip_against_daemon` rather than
standing up a second daemon, matching how `Park`/`Link`/`Sites`/`Doctor` already
extend that one sequential round trip.

### Problem 2 — AC2's test didn't test anything

The supervisor's finding: the first `cli_e2e.rs` addition hand-replayed
`run_status`'s two exchanges instead of calling `run_status`, so deleting
`lib.rs:240` kept it green. R2 (this spec, drafted for problem 1) requires a seam
only `run_status` calls in production.

**A design gap surfaced building that seam**, before any test ran: the natural
seam - extract "gather both responses, build `Rendered`" into a `pub async fn
status_outcome(json: bool) -> Rendered` - would still call `transport::exchange`,
which resolves the *real* default daemon socket
(`orcker_platform::ActivePaths::new().resolve()`), never the per-test daemon's
tempdir socket `cli_e2e.rs` builds. A test calling it would talk to whatever real
daemon happens to be at the default path (or none), not the wiring under test -
the same shape of defect the supervisor just found, one level deeper.

Fixed by extending `bin/orcker/src/transport.rs`'s existing default-path/explicit-path
split (`exchange` / `exchange_at`, the latter "factored out... so integration tests
can target a tempdir socket") one level up:

- `transport::default_sock() -> Result<PathBuf, ClientError>` - the resolution
  `exchange` already did inline, exposed so a caller needing it once for two
  exchanges (`orcker status`) does not resolve it twice.
- `status_outcome(sock: &Path, json: bool) -> Rendered` - takes the socket
  explicitly, mirroring `exchange_at`, and uses it for both exchanges.
- `run_status` resolves `default_sock()` once, then calls `status_outcome`, prints,
  converts to `ExitCode` - unchanged behavior (R3), same error text and exit code
  (69) on resolution failure as the original inline `?` produced.
- `exchange_at` gained a `#[cfg(not(unix))]` stub (didn't exist before - only
  `exchange` had one), mirroring the existing non-unix `exchange` stub verbatim,
  so `status_outcome` compiles on every target per the "mirror per-OS changes"
  rule, not just the unix build this was developed and tested on.

`cli_e2e.rs` now calls `orcker::status_outcome(&sock, true).await` directly and
parses the JSON `stdout` for a non-null `docker` key, rather than reconstructing
`Rendered` by hand.
