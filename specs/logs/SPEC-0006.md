## S2 — plan

### Decisions taken before writing code

**D1 — a container project reaches the router as a `ProxySite`, not as a new
`Site` kind.** R1 asks `orcker-core` for "a site kind for container projects",
but `Site` is the on-disk-served model (`document_root`, `web_subpath`, `php`)
and teaching the router a third `Route` arm would require changes in
`crates/orcker-proxy/`, which is **outside this spec's surface**. Reusing
`ProxySite` + `UpstreamTarget` is exactly the mechanism SPEC-0005 validated end
to end (`https://spike.test` with websockets, zero code delta), so
`ContainerProject::proxy_site()` consolidates onto it instead of duplicating a
second routing path. The spec's own Context section already retires R1's
"building on the SPEC-0005 delta" framing: there is no delta to build on, and
what this cycle adds is allocation, persistence and the registry (R2-R4).

**D2 — `orcker link` becomes the container link; the inherited native link
stays on the wire.** `orcker-cli.instructions.md` states the command surface is
designed fresh for this product and must not port a prior tool's vocabulary,
and PRD FR-021 defines `orcker link` as *the* project-adoption command. So
`Command::Link` maps to the new `Request::LinkProject`, while
`Request::Link` (native, used by the GUI) is untouched. `orcker::resolve_link`
stays public, so `bin/orcker/tests/cli_e2e.rs` (which calls it directly and
never goes through `map::to_request`) keeps exercising the legacy daemon path.
The one existing test edited is the `Command::Link` mapping assertion in
`bin/orcker/src/map.rs`, justified by R5's new signature. Confirmed with the
human before implementation.

**D3 — projects travel in their own `Response::Projects` reply, and
`orcker sites` issues two requests.** The first attempt grew `Response::Sites`
with a `projects` field; that broke `crates/orcker-mcp/tests/render.rs`, which
builds the variant with a full struct literal and is **outside this spec's
surface** - the same trap SPEC-0004 hit with `StatusReport`. So `ListProjects` /
`Projects` were added as their own message pair instead, and `orcker sites`
sends both and renders one table, exactly as `orcker status` already combines
`Status` and `EngineStatus` (`bin/orcker/src/lib.rs::run_status`). The payoff:
`Response::Sites` keeps its byte shape untouched, which
`response_sites_shape_is_unchanged_by_projects` now pins.

**D4 — `orcker.yml` is read from the project, never mirrored into
`orcker.toml`.** FR-024 AC1 requires a clone on machine B to reproduce machine
A from the repo alone, so the project file stays the source of truth for
`php`/`db`/`preset`; `orcker.toml` persists only the registry entry (name,
root, port, secure). Known ceiling: the daemon reads each project's
`orcker.yml` when answering `ListSites`, which is polled; if that ever costs,
it caches exactly like the existing `is_wordpress` cache.

**D5 — no YAML dependency.** The spec explicitly withholds authorization, so
`orcker_yml.rs` is a hand-written strict reader for the flat v1 schema.
Forward-compat rule: top-level `key: value` lines are read, unknown keys are
ignored, and any indented or `- ` line is skipped as nested content belonging
to an unknown key.

### Scope guards

Out of scope and deliberately untouched: stack generation on link, `park` for
container projects, compose lifecycle, port-range configurability, FR-023 file
ownership, and `docs/reference/orcker-yml.md` (FR-024 AC2, Phase 1).

the router forwards `spike.test` to `127.0.0.1:20000`, and `orcker secure`

(privileged bind, embedded DNS) are inherited and were already proven by
SPEC-0005 against the same stack. A human can close the literal form with
`orcker elevate ports resolver` and a browser.
